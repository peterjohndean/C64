; PURPOSE
; -------
; Decimal string <-> float conversion, in the spirit of BASIC's
; VAL()/STR$() but implemented directly against FP_CORE_PROC
; rather than BASIC's own FAC routines.
;
; ROUTINE INVENTORY
; -------------------
;   FP_FROM_ASCII_PROC      - parse a decimal string into FP1
;   FP_FROM_ASCII24_PROC    - parse with split integer/fraction
;                              accumulators for better precision
;   FP_FROM_ASCII_SCI_PROC  - parse optional scientific notation
;   FP_TO_ASCII_PROC        - format FP1 as fixed-point decimal
;   FP_TO_ASCII24_PROC      - fixed-point formatter with a 24-bit
;                              integer-part path
;   FP_TO_ASCII_SCI_PROC    - format FP1 as scientific notation
;
; SCOPE - READ THIS BEFORE RELYING ON EITHER ROUTINE
; -----------------------------------------------------
; These are deliberately NOT a full free-format implementation
; like BASIC's own FOUT/VAL (which handle scientific notation,
; arbitrary magnitude, and BASIC's specific rounding/significant-
; digit rules). What's here:
;
;   FP_FROM_ASCII_PROC accepts: an optional leading + or -, digits,
;   at most one decimal point, more digits. NO exponent notation
;   ("1E10" is not understood - it will parse as "1", stop at 'E').
;   An empty string, or a string with no digits at all, returns
;   with carry set and FP1 left at 0.0.
;
;   FP_FROM_ASCII24_PROC accepts the same non-exponent grammar as
;   FP_FROM_ASCII_PROC, but avoids the combined-digit precision loss
;   by accumulating the integer and fractional parts separately.
;
;   FP_FROM_ASCII_SCI_PROC extends that parser with an optional
;   E/e exponent suffix and scales by repeated multiply/divide by
;   10. It still requires at least one mantissa digit.
;
;   FP_TO_ASCII_PROC produces a fixed-point (never scientific
;   notation) string: an optional '-', the integer part, and a
;   caller-specified number of fractional digits. The integer part
;   is extracted via FP_TO_INT16_PROC, so values whose magnitude is
;   >= 65536 are OUT OF SCOPE for this routine.
;
;   FP_TO_ASCII24_PROC raises the fixed-point integer-part ceiling
;   to signed 24-bit range. FP_TO_ASCII_SCI_PROC avoids fixed-point
;   width limits by printing one leading digit and an exponent.
;
; Both routines expect PETSCII/ASCII digit codes ($30-$39 for
; '0'-'9', $2D for '-', $2B for '+', $2E for '.') - these happen to
; be identical in PETSCII and ASCII, so this works whether the
; string came from KERNAL_CHRIN, a screen-code buffer that's been
; translated, or ca65 string data, as long as the active .charmap
; produces those exact byte values for these non-letter characters.
; The scientific-notation E/e marker is the exception: see
; lib_fp_from_ascii_sci.s, lib_fp_to_ascii_sci.s, and tr_ascii_sci.s
; for the raw-PETSCII handling required there.
; ============================================================
